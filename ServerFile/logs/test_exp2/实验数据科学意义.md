## Fig 1 — 任务完成率热力图 (TCR Heatmap)

**文件**: `fig1_tcr_heatmap`

### 科学定位
任务完成率（Task Completion Rate, TCR）是评估端到端系统可用性的**最核心指标**。本热力图将 TCR 沿**难度等级（L1–L3）× 语义类型（5类）**二维展开，构成一个 3×5 的性能矩阵。

### 论证功能
1. **覆盖性验证**：证明实验设计覆盖了从基础运动到复合任务的完整指令空间，避免"只挑容易的测"的质疑。
2. **短板定位**：通过色阶直观暴露系统在特定难度×语义组合上的薄弱环节（如"L2 × 语义修饰符"），为后续改进指明方向。
3. **交叉效应分析**：揭示难度与语义类型之间是否存在交互效应——即某些语义类型是否在高难度下特别容易失败，这对理解 LLM 的指令理解边界至关重要。

### 论文写作建议
- 适合放在**实验结果章节**的开头，作为全局概览图。
- 论文中应重点讨论**非满分单元格**的成因分析，例如"语义修饰符类指令在 L2/L3 难度下失败，原因是 LLM 对修饰语的参数化映射能力不足"。
- 与 Fig 7 (SFS 分解) 形成"宏观→微观"的分析闭环。

## Fig 2 — 延迟分布箱线图 (Latency Boxplot)

**文件**: `fig2_latency_boxplot`

### 科学定位
对于无人机实时控制系统，**延迟**直接决定系统的实际可部署性。本图将延迟拆分为两个正交维度：
- **推理延迟**（Inference Latency）：LLM API 调用耗时，反映模型推理能力与网络条件。
- **执行耗时**（Execution Time）：生成代码在无人机上的物理执行时间，反映代码质量与任务复杂度。

### 论证功能
1. **实时性评估**：量化系统从接收指令到完成执行的端到端延迟，判断是否满足无人机控制的实时性要求。
2. **难度–延迟关系**：箱线图按 L1/L2/L3 分组，揭示指令复杂度对延迟的影响规律（通常 L3 推理延迟显著高于 L1，因为 LLM 需要生成更复杂的代码）。
3. **离群值分析**：箱线图的异常点（outliers）指示系统在特定指令上的异常行为（如网络超时、代码执行死循环），为安全机制设计提供依据。
4. **瓶颈识别**：通过对比推理延迟与执行耗时的相对比例，识别系统瓶颈是在"理解阶段"（LLM侧）还是"执行阶段"（无人机侧）。

### 论文写作建议
- 适合放在**实时性分析**小节。
- 应结合具体数值讨论"对于无人机控制场景，L1 指令的中位推理延迟为 X 秒，满足/不满足实时控制的 Y 秒阈值要求"。
- 离群值应在正文中逐一解释成因。

## Fig 3 — 综合评估指标雷达图 (Radar Chart)

**文件**: `fig3_radar_metrics`

### 科学定位
雷达图将系统的**六维综合评估指标**（PSR、TCR、CA、SFS、GR、EE）映射到极坐标空间，构成系统能力的"指纹图"。

### 论证功能
1. **多维均衡性评估**：单一指标无法全面反映系统能力。雷达图直观展示系统在各维度上的均衡程度——一个理想系统的雷达图应接近正六边形。
2. **短板维度识别**：凹陷的维度立即暴露系统的薄弱环节（如 EE 偏低说明执行效率有优化空间）。
3. **跨系统对比基线**：雷达图提供了标准化的可视化框架，未来若引入其他 LLM（如 GPT-4、Claude）进行对比实验，可在同一雷达图上叠加多条曲线。
4. **指标定义的合理性验证**：六个指标是否能全面覆盖系统能力的各个方面，雷达图的形状可以辅助判断是否存在冗余维度或缺失维度。

### 六维指标定义
| 指标 | 全称 | 测量内容 |
|------|------|----------|
| PSR | 解析成功率 | LLM 生成的代码能否被 Python 解释器成功解析 |
| TCR | 任务完成率 | 无人机是否成功执行了指令描述的行为 |
| CA | 条件分支准确率 | 对含条件判断的指令，LLM 是否选择了正确的分支 |
| SFS | 语义保真度评分 | 生成代码与自然语言指令的语义一致性（四维加权） |
| GR | 泛化鲁棒性 | 对未见过的指令表述（zero-shot），系统是否仍能正确执行 |
| EE | 执行效率 | 实际执行时间与理论最优时间的比值 |

### 论文写作建议
- 适合放在**实验结果总结**处，作为"一图概括系统能力"的可视化。
- 应在图注中列出六个指标的精确定义和计算公式。
- 若进行多模型对比实验，此图是最佳的可视化载体。

## Fig 4 — 指令时间分解 (Time Breakdown)

**文件**: `fig4_time_breakdown`

### 科学定位
水平堆叠条形图将**每条指令**的总耗时分解为推理延迟和执行耗时两部分，按总耗时降序排列，构成一个指令级的性能剖面图。

### 论证功能
1. **指令粒度分析**：不同于 Fig 2 的统计分布视角，本图保留了每条指令的个体信息，便于进行案例分析。
2. **推理–执行比例可视化**：堆叠结构直观展示每条指令中"思考时间"与"行动时间"的比例，揭示 LLM 在不同指令类型上的推理负载差异。
3. **长尾识别**：降序排列使"耗时异常长"的指令立即可见，这些指令往往对应系统最困难的挑战（如需要多步视觉搜索的复合任务）。
4. **安全超时阈值校准**：为系统的超时保护机制（如 60 秒 watchdog）提供数据支撑——若大部分指令在 30 秒内完成，则 60 秒超时是合理的。

### 论文写作建议
- 适合放在**案例分析**小节。
- 应挑选 2–3 条典型指令进行深入分析："指令 X 推理延迟占总耗时的 Y%，原因是..."
- 与安全机制章节中的超时阈值设计形成呼应。

## Fig 5 — 各难度等级多指标对比 (Difficulty Metrics)

**文件**: `fig5_difficulty_metrics`

### 科学定位
分组柱状图将三个核心指标（TCR、SFS、EE）沿**难度等级**（L1/L2/L3）维度展开，配合误差线展示组内方差。

### 论证功能
1. **难度梯度验证**：证明实验设计的三级难度体系确实体现了递增的挑战——如果 L1–L3 的指标没有显著差异，说明难度分级设计有问题。
2. **降级规律量化**：量化系统性能随指令复杂度增加的衰减速度。理想情况下，TCR 应缓慢下降，而非断崖式跌落。
3. **指标间差异分析**：通过对比同一难度等级下不同指标的表现，揭示系统的能力特征。例如"TCR 高但 SFS 低"意味着无人机完成了任务但动作不够精确。
4. **误差线的统计意义**：标准差反映组内一致性——大误差线说明该难度等级内的指令表现差异大，提示指令设计可能存在异质性。

### 论文写作建议
- 适合放在**难度层次分析**小节。
- 应对 Y 轴的动态范围做说明："为突出各等级间差异，Y 轴范围根据数据动态调整"。
- 结合 Fig 1 的热力图，形成"按难度看"和"按语义类型看"的双视角分析。

## Fig 7 — 语义保真度评分分解 (SFS Breakdown)

**文件**: `fig7_sfs_breakdown`

### 科学定位
语义保真度评分（Semantic Fidelity Score, SFS）是本研究提出的**核心评估指标**，借鉴了 ALFRED 基准的 Goal-Condition 评估范式。本图将每条指令的 SFS 分解为四个子维度的堆叠条形图。

### 四维分解定义
| 子维度 | 评估内容 | 示例 |
|--------|----------|------|
| **目标准确性** (sfs_target) | LLM 是否正确识别了指令中的操作对象 | "红色气球"而非"蓝色小球" |
| **参数精确性** (sfs_param) | 数值参数（距离、角度、速度）是否准确映射 | "2米"映射为 `2.0` 而非 `5.0` |
| **动作正确性** (sfs_action) | 生成的动作类型是否与指令意图一致 | "靠近"映射为前进而非后退 |
| **执行有效性** (sfs_execution) | 生成代码的执行结果是否达到了预期效果 | 无人机确实到达了目标位置 |

### 论证功能
1. **失败归因分析**：当 SFS 总分不满时，堆叠分解可精确定位是"理解错了对象"、"参数映射有误"、"动作选错了"还是"代码执行出了问题"。
2. **LLM 能力边界刻画**：通过统计各子维度的失分频率，量化 LLM 在视觉语言控制场景下的具体能力边界。例如"目标识别准确率高，但参数映射是主要瓶颈"。
3. **改进方向优先级排序**：失分最多的子维度应优先改进——如果"参数精确性"普遍偏低，则应改进提示词中的参数约束规则。
4. **ALFRED 范式适配验证**：证明 ALFRED 的 Goal-Condition 评估范式可以有效迁移到无人机控制场景。

### 论文写作建议
- 适合放在 **SFS 指标深度分析**小节，是论文的**核心图表之一**。
- 应在方法论章节详细阐述 SFS 的设计动机和四维权重分配。
- 挑选 3–4 条典型指令（满分、部分失分、严重失分）进行案例对比分析。

## Fig 9 — SFS 与执行效率关联散点图 (SFS vs EE Scatter)

**文件**: `fig9_sfs_vs_ee_scatter`

### 科学定位
散点图揭示语义保真度（SFS）与执行效率（EE）之间的**协变关系**，是 Nature 多面板信息架构中 Level 3（Relationship）层级的核心图表。

### 论证功能
1. **质量–效率权衡分析**：在工程系统中，质量与效率通常存在权衡（trade-off）。散点图回答"高语义保真度是否以牺牲执行效率为代价"这一关键问题。
2. **象限分析**：
   - **右上象限（高质·高效）**：系统的理想工作区间——指令理解准确且执行迅速。
   - **左下象限（低质·低效）**：系统的最差表现区间——需要深入分析这些指令的共性特征。
   - **右下象限（高质·低效）**：语义理解正确但执行缓慢，通常对应复杂的多步任务。
   - **左上象限（低质·高效）**：快速但错误的执行，可能对应硬规则拦截后的默认行为。
3. **难度分层着色**：按 L1/L2/L3 着色后，可观察不同难度等级的指令是否聚集在不同象限，验证"难度越高，质量和效率是否同时下降"的假设。
4. **中位数参考线**：虚线交叉将散点分为四个象限，提供直观的基准判断。

### 论文写作建议
- 适合放在**关联性分析**小节，是论文中**最具方法论创新性**的图表之一。
- 应讨论散点的聚集/分散模式，以及是否存在明显的正相关/负相关趋势。
- 若数据点足够多，可考虑添加线性回归拟合线和 R² 值。

## Fig 10 — 各语义类型指标对比 (Semantic Type Metrics)

**文件**: `fig10_semantic_type_metrics`

### 科学定位
与 Fig 5（按难度分析）构成**正交维度**的对照——本图按**语义类型**维度分析 TCR 和 SFS。

### 五类语义类型定义
| 类型 | 定义 | 代表指令 |
|------|------|----------|
| **基础运动** | 单一运动原语（前进、转向、升降） | "向左飞两米" |
| **目标定位** | 需要视觉感知定位目标 | "飞向红色气球" |
| **语义修饰符** | 含速度、距离等语义约束的修饰 | "缓慢后退2米" |
| **条件分支** | 含 if-else 条件逻辑 | "如果看到小车就靠近" |
| **复合任务** | 多步骤串联的复杂任务 | "先向左飞再向右飞" |

### 论证功能
1. **语义理解能力分层**：不同语义类型对 LLM 的能力要求不同——基础运动可通过硬规则覆盖，而条件分支和复合任务需要 LLM 的代码生成能力。
2. **硬规则 vs LLM 有效性对比**：如果"基础运动"类 TCR 和 SFS 都很高，而"语义修饰符"类偏低，则说明硬规则拦截对简单指令有效，但 LLM 在处理语义修饰时仍有不足。
3. **指令集设计验证**：五类语义类型的表现差异验证了指令集设计的合理性——类型间应有可区分的难度梯度。
4. **混合架构贡献度分析**：结合硬规则覆盖率和 LLM 生成率，可量化混合架构中各模块的贡献度。

### 论文写作建议
- 适合放在**语义类型分析**小节，与 Fig 5 形成"难度维度 vs 语义维度"的交叉分析。
- 应重点讨论表现最差的语义类型，分析其失败根因。
- 与系统架构章节中"硬规则拦截 vs LLM 代码生成"的设计决策形成数据支撑。

## Fig 11 — Core 指令集 vs Zero-shot 泛化对比 (Core vs Zero-shot)

**文件**: `fig11_core_vs_zeroshot`

### 科学定位
使用 **alpha 渐变编码**（同色系不同透明度）对比 Core 指令集（预设指令）与 Zero-shot 指令（未见过的表述）的性能差异，直接验证系统的**泛化鲁棒性（GR）**。

### 论证功能
1. **泛化能力验证**：这是论文中**最关键的验证之一**。如果 Zero-shot 指令的 TCR/SFS/EE 与 Core 指令相当，则证明系统不是"过拟合"于预设指令集，而是真正理解了自然语言语义。
2. **实际部署可行性论证**：在真实应用场景中，用户不会按照预设模板说话。Zero-shot 性能直接决定系统的实际可用性。
3. **Alpha 编码的设计语言**：使用同色系不同透明度（深色 = Core, 浅色 = Zero-shot）而非不同颜色，传达两者属于"同一系统的不同评估条件"而非"不同系统"的语义。
4. **样本量对比**：图例中标注 n 值（如 Core n=15, Zero-shot n=3），提醒读者注意样本量差异对统计推断的影响。

### 论文写作建议
- 适合放在**泛化性验证**小节，是论文**核心论证链**的关键环节。
- 应在方法论中明确 Zero-shot 指令的生成方式（是否由独立人员编写、是否刻意避免与 Core 指令的表述重叠）。
- 讨论 Zero-shot 性能与 Core 性能的差值是否在统计上显著（若样本量足够，可加 t-test p 值）。
- 若 Zero-shot 性能反而高于 Core，应分析原因（可能是 Zero-shot 指令恰好更简单，或样本量过小导致偶然性）。
